OpenProse, on the command line.

A walk through what an operator actually sees: the boot banner, the contract, a single run end-to-end, what happens when something fails, and what rolls up at the end of the day.

SHELLzsh · RUNTIMEopenprose-v0.42 · HOSTridgeline-ops
§ 01

The runtime, on boot.

When the OpenProse runtime starts, it does three things in order: resolves the manifest at ~/responsibilities/openprose.lock, binds the inputs each responsibility declares it requires, and tells you which responsibilities are running, which are holding, and which are quietly archived. Boot is informational. Nothing has been delivered yet.

Exhibit 1boot · ridgeline-ops · 06:00 ET
sarah@ridgeline-ops · openprose boot
┌─────────────────────────────────────────────────────────────┐ │ OpenProse runtime · v0.42.0 · openprose.ai/runtime │ │ a literary computer · for programs you can read & prove │ └─────────────────────────────────────────────────────────────┘
[ ok ] resolving manifest at ~/responsibilities/openprose.lock
[ ok ] 12 responsibilities loaded · 8 active · 2 holding · 2 archived
[ ok ] connecting to data warehouse … bound (3a8f29c)
[ ok ] connecting to weather API … bound (rate-limited, 0.94 of cap)
[ warn ] tenant-anomaly-watch: precision regressed wk 16→18, holding delivery
[ ok ] runtime ready · listening on cadence · Mon 09:00:00 ET

— twelve responsibilities, two of them holding. The held ones get explained later.

§ 02

The contract.

Every responsibility is a single .prose file. The whole spec — what it requires, what it ensures, who it's signed by, where it delivers — fits in fifteen lines. There is no template. There is no DSL. The file is plain language; the runtime is what makes it operate.

A program is a document with guarantees. weekly-energy-digest.prose, the file you're about to read, is one of those documents.

Exhibit 2cat · weekly-energy-digest.prose · v42
~/responsibilities/weekly-energy-digest.prose
sarah@ridgeline-ops ~/responsibilities $ cat weekly-energy-digest.prose
responsibility: weekly-energy-digest owner: sarah.k @ ridgeline-ops cadence: mondays @ 09:00 ET requires: - data_warehouse_url # the meter records, all 40 buildings - codebase_ref # commit 3a8f29c · verified - weather_api # for HDD/CDD normalization ensures: - weekly growth findings - anomaly notes << 2% false-positive - delivered Mondays @ 09:00 ET · verified · signed tone: "executive-friendly. flag anomalies. no jargon." # weather API: this fails closed every other Wednesday # last edit: maya bumped the threshold from 0.05 → 0.02 after # the building 14 false alarm. she was right. deliver: - slack #ops-energy - email digest@ridgeline.example audit: retain 7 years · sign every delivery

— the comment lines beginning with # are Sarah's actual notes, kept in the file.

§ 03

A run, end-to-end.

Each Monday at 09:00 ET, the runtime resolves the requires-clauses, executes the work, and verifies the result against each ensures-clause. If the score crosses threshold, the brief delivers; if not, the runtime holds. --dry-run is the same flow, with no delivery sent — useful for inspecting the trajectory before going live.

Exhibit 3op run --dry-run · v42
op run weekly-energy-digest --dry-run
sarah@ridgeline-ops ~/responsibilities $ op run weekly-energy-digest --dry-run
→ resolving requires … → data_warehouse_url ok (40 buildings · 7,238 records) → codebase_ref ok (3a8f29c · verified) → weather_api ok (HDD = 142, CDD = 0) → executing … → gathered: 7,238 meter records · 39 weather samples → normalized: $/sqft against HDD baseline → anomalies: 3 flagged (building 12, 14, 31) → drafted: 247-word brief · 3 callouts · 1 chart → verifying against contract … → weekly growth findings ✓ pass → anomaly FP rate << 2% ✓ pass (0.7%) → tone: "executive-friendly" ✓ pass (eval 0.97) → score: 0.97 (+0.01 from v41) → would deliver to: #ops-energy, digest@ridgeline.example → [dry-run only · no delivery sent]

— each ensures-clause is checked individually. The runtime never quietly aggregates passes.

§ 04

When something fails.

The runtime never fails silently. If a contract clause regresses, it pages the on-call and writes the regression into the run log with as much causal detail as it can construct. op why is the operator's tool for asking, "what happened, and what's the recommended patch?" The answer is always specific: which clause, which run, which suggested edit.

Exhibit 4op why · tenant-anomaly-watch · held v18
op why tenant-anomaly-watch
sarah@ridgeline-ops ~/responsibilities $ op why tenant-anomaly-watch
holding · v18 · last 3 runs: → v16 · score 0.91 · delivered → v17 · score 0.83 · delivered (eval barely over threshold) → v18 · score 0.74 · held (threshold was 0.80) root cause likely: utility API rate-limited Tue 22:14, returned a partial dataset. the contract didn't specify what to do with a partial fetch. suggested spec patch: requires: - utility_api # add: on partial fetch, hold delivery · don't extrapolate // jamie, this is a spec issue, not a model issue. sit with me Tue? // — sk

— the personal asides at the bottom are the operator's notes back to her team. They live with the run.

§ 05

What rolls up at the end of the day.

By 09:01 ET on a Monday, the day's deliveries are decided. op log --tail 5 is a one-screen rollup: which responsibilities ran, what they scored, where they delivered, which one held. Nothing else needs to be opened. If you wanted, you could leave it at that.

Exhibit 5op log --tail 5 · 2026-05-04
op log --tail 5
sarah@ridgeline-ops ~/responsibilities $ op log --tail 5
2026-05-04 09:00:42 delivered weekly-energy-digest v42 0.97 → #ops-energy 2026-05-04 09:00:14 delivered on-call-rotation-brief v52 0.99 → #ops 2026-05-04 08:58:33 holding tenant-anomaly-watch (precision) v18 0.74 → paged on-call 2026-05-04 08:55:01 delivered end-of-week-anomalies v18 0.92 → #ops 2026-05-03 17:14:08 delivered vendor-payment-summary v33 0.95 → accounting
sarah@ridgeline-ops ~/responsibilities $ _
§ end

That's the whole interface.

Five commands cover the day-to-day: op status, op run, op why, op log, op patch. The contract sits on disk, version-controlled. The runtime ships briefs on cadence. The held ones get a page; the delivered ones get signed. Sarah is in Building 14 looking at a boiler when the brief lands. She doesn't open it until lunchtime. That is the point.
